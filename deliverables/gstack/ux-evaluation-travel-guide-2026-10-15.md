## 4. 改进建议（5 条）

### 建议 1：修复直辖市被误判为省份（P0）

| 项 | 内容 |
|---|---|
| **问题描述** | `app.js:50` 的 `PROVINCES` 数组把北京/上海/天津/重庆四个直辖市与省份混在一起。`detectProvince()` 命中后，`submitCity()` 直接 return 并提示「是一个省份」，导致榜单首卡点击必然失败 |
| **改进方案** | 把直辖市从 `PROVINCES` 拆出为独立常量 `MUNICIPALITIES`；`detectProvince()` 先判断是否为直辖市，若是则直接放行进入生成流程。省份提示文案同步修正为「请输入具体城市名（如：北京、上海）」 |
| **预期效果** | 恢复 17% 的"一键生成"入口；SUS 第 6/9 题各 +1 → **SUS 77.5 → 82.5（达标）**；任务完成率 85.7% → 100% |
| **实现难度** | ⭐ 极低（约 10 行改动 + 单测） |
| **优先级** | **P0** |

### 建议 2：AI 失败时快速降级并如实告知（P1）

| 项 | 内容 |
|---|---|
| **问题描述** | AI 全链路失败时静默回退本地数据，用户等待 12 s 却不知道内容来源；加载文案仍宣称「AI 正在分析…」，与实际不符 |
| **改进方案** | ① AI 请求设较短超时（如 8 s）并在首个 provider 失败时即并发尝试备选，而非串行等待；② 回退时把加载文案改为「AI 暂不可用，正在用本地数据库为你生成…」；③ 结果页顶部加数据来源徽章（「AI 生成」/「本地数据库 · 可能滞后」） |
| **预期效果** | 感知等待从 12 s 降至 5-8 s；消除"被欺骗感"；呼应阶段一产品评审提出的"数据真实性透明化" |
| **实现难度** | ⭐⭐ 低 |
| **优先级** | **P1** |

### 建议 3：修正结果页章节编号（P2）

| 项 | 内容 |
|---|---|
| **问题描述** | 实测章节序列 `00/01/02/03/03/04/07` —— `03` 重复、`04` 跳到 `07`。编号硬编码在 `renderGuide()` 各区块中，条件渲染时未重新计算 |
| **改进方案** | 把编号改为渲染时按实际输出顺序动态分配（维护一个自增计数器），而非各处硬编码 `'03'`/`'05'` |
| **预期效果** | 消除肉眼可见的专业度瑕疵；长文档的层次感恢复正常 |
| **实现难度** | ⭐⭐ 低（改 `renderGuide` 的编号生成逻辑） |
| **优先级** | **P2** |

### 建议 4：为长攻略增加目录导航（P2）

| 项 | 内容 |
|---|---|
| **问题描述** | 攻略正文高 3819 px（约 4.5 屏），含 7 个区块，但无目录或锚点，用户只能滚动寻找"预算""美食"等目标区块 |
| **改进方案** | 结果页左侧（桌面）/顶部（移动）加粘性目录，列出各区块标题并支持点击跳转；滚动时高亮当前区块（IntersectionObserver，可复用阶段五的 `initScrollReveal` 基础设施） |
| **预期效果** | 长文检索效率显著提升；复访用户可直接跳到关心区块 |
| **实现难度** | ⭐⭐⭐ 中（约 1 轮迭代） |
| **优先级** | **P2** |

### 建议 5：榜单与文案对齐（P2）

| 项 | 内容 |
|---|---|
| **问题描述** | 标题「本周值得一去的地方 / 编辑精选」但实际榜单混入大量冷门城市（漯河、株洲、许昌…），与"编辑精选"的语义落差明显；且榜单会随日期种子变化，稳定性差 |
| **改进方案** | ① 榜单改为「热门目的地」等更中性的表述，或真正按季节+热度人工编排 Top 12；② 优先展示用户认知度高的一线与新一线城市；③ 保留 2-3 个"小众推荐"位并明确标注「编辑小众推荐」 |
| **预期效果** | 首屏推荐可信度提升；点击率改善 |
| **实现难度** | ⭐⭐ 低（调整排序权重与文案） |
| **优先级** | **P2** |

## 5. 新功能建议（3 条）

### 功能 1：行程可编辑与导出（用户价值最高）

| 项 | 内容 |
|---|---|
| **用户价值** | 当前生成的攻略是"只读"的。真实用户几乎一定会调整——删掉不感兴趣的景点、加一天、换成亲子向。可编辑 + 导出为日历/备忘录，是从"看攻略"到"用攻略"的关键一跳，直接决定留存 |
| **实现难度** | ⭐⭐⭐⭐ 高（需引入编辑态、本地持久化、导出格式转换） |
| **优先级** | **P1** |

### 功能 2：离线可用（PWA 深化）

| 项 | 内容 |
|---|---|
| **用户价值** | 旅行场景天然弱网/无网（景区、山区、境外漫游）。当前 PWA 骨架已就绪（阶段二已修复 SW 注册），但只缓存静态资源。把已生成的攻略、收藏、照片纳入离线可用，是**旅行类产品的刚需** |
| **实现难度** | ⭐⭐⭐ 中（IndexedDB 存攻略 + SW 缓存策略扩展） |
| **优先级** | **P1** |

### 功能 3：数据来源与更新时间透明化

| 项 | 内容 |
|---|---|
| **用户价值** | 旅行决策对数据可信度极度敏感。明确标注「天气：模拟数据 / 更新于 10-15」「攻略：AI 生成 / 本地数据库」可避免信任崩塌；同时为用户提供"这个数据能不能信"的判断依据 |
| **实现难度** | ⭐ 极低（后端已在响应中返回 `source` / `lastUpdated`，只需前端展示） |
| **优先级** | **P0**（与建议 2 合并实施） |

## 7. 已知局限

1. **本次评估基于本地回退路径**。AI 提供方全部不可用（Agnes 401 / OpenAI 403 / 和风天气 403），因此走查的是**降级后的真实用户路径**。AI 正常时的体验（内容质量、生成速度）**未评估**。
2. **SUS 为自评**，非真实用户调研。样本量 1（评估者视角），不能替代多用户量表调研。
3. **仅覆盖 3 个核心场景**，未覆盖：AI 修图、票务/酒店比价跳转、照片上传、PWA 安装、多城市批量生成。
4. **仅 Chromium 内核**（系统 Edge），Firefox / Safari 未覆盖。

### 新发现：生成耗时波动大（12.1 s ~ 43.3 s）

修复后复测时观察到：同一路径（点击榜单卡片生成攻略）耗时从场景 A 的 **12.1 s** 变为 **43.3 s**，波动达 3.6 倍。

**推测原因**（未做逐层埋点验证）：AI 提供方串行重试的固定等待窗口 + 新城市天气缓存冷启动（`weatherSync` 每次外部请求 6 s 超时，冷缓存下需多次）。
